## 0. 한 줄 요약

1년 차 거래에서 A-Priori와 PCY로 찾은 연관 규칙이 2년 차에도 성립하는지, 그리고 그 규칙이 "가장 많이 팔린 상품" 기준선보다 다음 상품을 더 잘 맞히는지 검증한다. 검증된 규칙만 Upstage Solar 에이전트가 도구 호출로 조회해 답한다.

## 1. 질문과 범위 (루브릭 25점)

### 질문

> 2009-12 ~ 2010-11 (1년 차) 거래에서 찾은 연관 규칙이 2010-12 ~ 2011-11 (2년 차)에도 성립하는가? 그리고 그 규칙이 인기 상품 기준선보다 다음 상품을 더 잘 예측하는가?

### 왜 중요한가

소매점이 묶음 판매나 진열을 바꾸려면 규칙이 다음 시즌에도 성립해야 한다. 한 해에만 성립하는 규칙은 우연이거나 일회성 행사일 수 있다. 규칙이 인기 상품 추천보다 낫지 않다면 규칙 마이닝을 할 이유가 없다.

### 무엇이 답으로 인정되는가

결과에 따라 틀릴 수 있도록 판정 기준을 미리 정한다.

| 가설 | 측정 | "예"로 판정하는 조건 | "아니오"로 판정하는 조건 |
|---|---|---|---|
| H1 규칙 유지 | 1년 차 규칙 중 2년 차에도 confidence ≥ 0.5, lift > 1 인 비율 | 유지율이 셔플 null 모델의 유지율보다 높고, 1년 차 규칙 수가 null 모델 평균 규칙 수의 10배 이상 | 둘 중 하나라도 실패 |
| H2 예측 우위 | 2년 차 장바구니에서 상품 하나를 가리고 맞히는 HitRate@5 | 규칙 기반 − 인기 기준선 차이의 bootstrap 95% 신뢰구간 (1,000회, seed 0)이 0보다 위 | 신뢰구간이 0을 포함하거나 0보다 아래 |
| H3 에이전트 정확성 | 사전 작성한 질문 20개에 대한 답의 수치 인용 정확도 | 답에 인용된 support, confidence 값의 90% 이상이 규칙 표와 일치 | 90% 미만 |

## 3. 방법과 정당화 (루브릭 25점)

### 3.1 빈발 항목집합 (MMDS 6장)

- **A-Priori (§6.2):** 1차 패스에서 상품 빈도를 세고, 2차 패스에서 빈발 상품끼리의 쌍만 센다.
- **PCY (§6.3.1):** 1차 패스에서 쌍을 해시 버킷에 세어 두고, 빈발 버킷에 속한 쌍만 2차 패스 후보로 남긴다. 버킷 수와 해시 시드는 고정한다.
- 두 구현이 같은 빈발 쌍을 내는지 교재 예제와 실제 데이터에서 확인한다.
- 비교 지표: 2차 패스 후보 쌍 수, 최대 메모리 (`tracemalloc`), 실행 시간 (5회 중앙값).
- support 2%, 1%, 0.5%, 0.25% 네 수준에서 비교한다. 파일럿에서 support 1%의 2차 패스는 0.6초였다. 이 데이터는 메모리에 다 들어가므로 PCY의 이득이 작을 수 있다. support를 낮춰 후보 쌍이 늘어날 때 차이가 생기는지 재고, 차이가 없으면 없다고 보고한다.

### 3.2 규칙과 기준선

- 규칙: 빈발 쌍 {A, B}에서 A → B, B → A. 지표는 support, confidence, lift.
- 예측: 2년 차 장바구니마다 상품 하나를 가리고 (seed 0으로 선택), 남은 상품을 전건으로 갖는 규칙의 confidence 최댓값 순으로 상위 5개를 고른다. 5개가 안 되면 인기 상품으로 채운다.
- 기준선: 1년 차 판매 빈도 상위 상품 중 장바구니에 없는 5개.
- 평가 대상: 상품 2개 이상인 2년 차 장바구니.

### 3.3 우연한 규칙 통제 (MMDS §1.2 본페로니 원리)

support 1%에서만 후보 쌍 252,748개를 검사한다. 이만큼 검사하면 우연히 기준을 넘는 쌍이 생긴다.

- **null 모델:** (장바구니, 상품) 쌍 전체에서 상품 열만 무작위로 섞는다. 그러면 장바구니 크기와 상품별 등장 횟수가 그대로 유지되고, 상품 사이의 동시 구매 관계만 깨진다. 한 장바구니에 같은 상품이 두 번 들어가면 그 자리는 다시 섞는다. seed 0~4로 5회.
- null 데이터에 같은 마이닝을 돌려 기준을 넘는 규칙 수를 센다. 이 수가 "우연히 나오는 규칙 수"의 추정치다.
- support와 confidence 기준은 null 규칙 수가 실제 규칙 수의 10% 미만이 되는 값으로 정한다. 기준은 1년 차 데이터로만 정하고, 2년 차 결과를 본 뒤 바꾸지 않는다.

### 3.4 Solar 에이전트

- 모델: Upstage Solar (OpenAI 호환 chat completions, function calling 지원 모델). 11/10까지 접속 테스트를 하고 모델 ID를 기록·고정한다.
- 도구 (모두 파이프라인이 만든 규칙 표만 읽는다. 에이전트는 수치를 직접 계산하지 않는다):
  - `rules_for(product)`: 상품명 또는 코드로 관련 규칙 조회
  - `top_rules(min_support, min_confidence)`: 기준을 넘는 상위 규칙
  - `season_filter(period)`: 기간별 규칙. 1년 차를 11~12월과 나머지로 나눠 따로 마이닝한 표를 쓴다
- 평가 (H3): 팀원이 에이전트를 돌리기 전에 질문 20개와 정답(호출할 도구, 인용할 수치)을 먼저 쓴다. temperature 0으로 돌리고 대화 기록을 `results/agent_runs.jsonl`에 저장한다. 보고서 수치는 이 기록에서만 가져온다.
- 에이전트가 없다면: 규칙 수백 개를 사람이 표에서 직접 걸러 읽어야 한다. 에이전트의 역할은 질문을 도구 호출로 바꾸고 결과를 근거와 함께 설명하는 것이다.

### 3.5 고려했지만 버린 대안

| 대안 | 장 | 버린 이유 |
|---|---|---|
| MinHash + LSH로 비슷한 상품 찾기 | 3장 | Jaccard 유사도는 대칭이라 "A를 사면 B를 산다"는 방향을 표현하지 못한다. 상품 4,877개라 정확히 세는 것이 가능해 근사가 필요 없다 |
| SON, Toivonen 표본 알고리즘 | §6.4 | 데이터가 메모리에 다 들어가므로 여러 번 나눠 읽거나 표본을 쓸 이유가 없다 |
| 협업 필터링, UV 분해 | 9장 | 고객 ID가 필요한데 개인정보 최소화를 위해 삭제한다. 점수는 나오지만 사람이 읽을 수 있는 규칙이 나오지 않는다 |
| 스트림 빈도 추정 | 4장 | 데이터가 고정된 2년치라 스트림 처리가 필요 없다 |
| FP-Growth | 교재 범위 밖 | 과목 개념을 쓰는 조건에 맞지 않고, 결과는 A-Priori와 같다 |

| 버린 정보 | 질문과의 관계 | 확인 방법 |
|---|---|---|
| 수량과 가격 | 질문은 "함께 사는가"라서 수량은 무관하다. 다만 도매 구매가 많은 데이터라 큰 장바구니가 규칙을 좌우할 수 있다 | 장바구니 크기 상위 1% (약 400개)를 빼고 다시 돌려 규칙과 H1, H2 결과가 얼마나 바뀌는지 보고 |
| 고객 정체성 (재구매, 고객 간 차이) | 질문은 한 장바구니 안의 동시 구매라서 무관하다. 대신 같은 도매 고객이 반복 주문한 규칙이 "일반 규칙"처럼 보일 수 있다 | 삭제했으므로 확인할 수 없다. 이 한계를 보고서에 그대로 적는다 |
| 장바구니 안의 순서와 시각 | 송장 하나는 한 번에 결제되므로 순서 정보가 원래 없다 | 해당 없음 |

| 상품 설명 변형 | 같은 코드에 설명이 여러 개다. 코드로 묶으므로 무관하다. 반대로 다른 코드인데 사실상 같은 상품(색상 변형 등)은 따로 센다 | 모른다. 색상 변형 접미사(`A`, `B` 등)를 합쳤을 때 결과가 바뀌는지는 시간이 남으면 확인 |
| 취소와 반품 | 취소된 구매를 동시 구매로 세지 않기 위해 버린다 | 취소 송장 8,292개. 원 송장과 짝을 맞추지는 않는다 |
| 국가 | 영국이 92%라 규칙은 사실상 영국 규칙이다 | 보고서에 명시. 국가별 분석은 하지 않는다 |
| 3개 이상 조합 | 쌍 규칙만 주 결과로 쓴다 | 3개 조합은 개수만 보조 보고 |

## 5. 재현 가능성 (루브릭 15점)

```text
scripts/download_data.py   데이터 다운로드와 checksum 확인 (완료)
src/clean.py               전처리, 단계별 행 수를 results/cleaning_log.csv에 기록
src/apriori.py             A-Priori
src/pcy.py                 PCY
src/null_model.py          셔플 null 모델
src/evaluate.py            H1, H2 판정, bootstrap
src/agent.py               Solar 에이전트와 도구
src/run_all.py             전체 실행: python -m src.run_all
tests/test_textbook.py     교재 예제에서 A-Priori와 PCY 결과 확인
requirements.txt           버전 고정
```

- 깨끗한 체크아웃에서 `python scripts/download_data.py && python -m src.run_all` 두 명령으로 모든 표와 그림을 만든다.
- 시드: 상품 가리기, bootstrap, null 셔플, PCY 해시 모두 고정.
- 보고서의 그림과 표마다 만든 명령을 바로 아래 적는다.
- 에이전트 결과는 LLM이라 같지 않을 수 있다. 그래서 저장한 기록을 근거로 쓰고, 다시 돌리면 달라질 수 있다고 보고서에 적는다.
- `.env`의 API 키는 레포에 올리지 않는다.

| PCY가 A-Priori보다 나을 것이 없음 | 결과로 보고한다. 데이터가 메모리에 들어가는 규모라는 것이 이유이고, 그것 자체가 방법 선택의 근거다 |
| 규칙이 기준선을 못 이김 (H2 실패) | 실패도 답이다. 어떤 장바구니에서 지는지 (크기, 계절) 나눠 보고한다 |
| Solar API 접근 지연 | 11/10까지 확인. 늦어지면 도구 함수와 평가 질문을 먼저 만들고 에이전트는 마지막에 연결 |
| 대형 도매 장바구니가 결과를 좌우 | 4절 민감도 분석 |

## 9. 완료 조건

아래가 모두 참이면 프로젝트를 완료로 본다.

- [ ] 깨끗한 체크아웃에서 두 명령으로 모든 결과가 다시 나온다
- [ ] 교재 예제 테스트가 통과한다
- [ ] A-Priori와 PCY의 빈발 쌍이 네 support 수준에서 모두 같다
- [ ] H1, H2, H3에 대해 미리 정한 기준으로 예/아니오 판정이 나와 있다
- [ ] 버린 정보 표의 각 줄에 확인 결과 또는 "모른다"가 적혀 있다
- [ ] 보고서의 모든 그림 아래에 만든 명령이 있다
- [ ] 장표의 모든 수치가 보고서의 표나 그림으로 추적된다
