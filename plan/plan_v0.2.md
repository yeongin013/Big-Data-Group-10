## 0. 한 줄 요약

1년 차 거래에서 A-Priori와 PCY로 찾은 연관 규칙이 2년 차에도 성립하는지, 그리고 그 규칙이 인기 상품 기준선보다 다음 상품을 더 잘 맞히는지 검증한다. Upstage Solar 에이전트는 규칙 표를 도구로 조회해 답하고, 도구 없는 Solar보다 정확한지 따로 검증한다.

## 1. 질문과 범위 (루브릭 25점)

### 질문

> 2009-12 ~ 2010-11 (1년 차) 거래에서 찾은 연관 규칙이 2010-12 ~ 2011-11 (2년 차)에도 성립하는가? 그리고 그 규칙이 인기 상품 기준선보다 다음 상품을 더 잘 예측하는가?

### 왜 중요한가

소매점이 묶음 판매나 진열을 바꾸려면 규칙이 다음 시즌에도 성립해야 한다. 한 해에만 성립하는 규칙은 우연이거나 일회성 행사일 수 있다. 규칙이 인기 상품 추천보다 낫지 않다면 규칙 마이닝을 할 이유가 없다.

### 고정한 기준 (2026-11-04, 이 문서의 커밋 시점에 동결)

- 주 support 기준: **1%** (1년 차 장바구니 19,743개 중 198개 이상)
- 규칙 기준: **confidence ≥ 0.5, lift > 1**
- 장바구니: 송장 하나 = 상품 코드의 집합 (같은 코드가 여러 줄이어도 한 번)
- 이 값들은 null 모델이나 2년 차 결과를 본 뒤 바꾸지 않는다. support 2%, 0.5%, 0.25%는 PCY 성능 비교와 민감도 보고에만 쓴다.

**사전 노출 고지:** 아래 파일럿에서 2년 차 유지율을 이미 한 번 봤다. 그래서 H1의 50% 기준은 완전한 사전 등록이 아니다. 보고서에 이 사실을 적는다.

### 무엇이 답으로 인정되는가

| 가설 | 측정 | "예" 조건 (모두 충족) |
|---|---|---|
| H1a 규칙이 우연이 아님 | 1년 차 실제 규칙 수 vs null 1년 차 규칙 수 (100 seed) | 실제 규칙 수 > null 규칙 수의 최댓값 (경험적 p < 0.01) |
| H1b 규칙 유지 | 1년 차 규칙 중 실제 2년 차에서 confidence ≥ 0.5, lift > 1 인 비율 | 유지율 ≥ 50%, 그리고 null 2년 차 유지율 최댓값 + 20%p 이상 |
| H2 예측 우위 | 2년 차 HitRate@5, 규칙 기반 − 인기 기준선 | 대응 bootstrap 95% 신뢰구간의 하한 ≥ +2%p |
| H3 에이전트 정확성 | 질문 25개 문항별 정답률 | 도구 사용 Solar ≥ 80%, 그리고 도구 없는 Solar보다 30%p 이상 높음 |

조건을 하나라도 못 넘으면 그 가설은 "아니오"다.

정의:

- **H1b 유지:** 2년 차 support 조건은 두지 않는다. 규칙의 상품 중 하나라도 2년 차에 팔리지 않았으면 "유지 안 됨"으로 센다.
- **null 2년 차 유지율:** 실제 1년 차 규칙을 셔플한 2년 차 데이터(100 seed)에서 같은 기준으로 잰 유지율이다.
- **보조 보고 (판정 아님):** 1년 차와 2년 차 confidence, lift의 Spearman 상관. 그리고 "2년 차 confidence ≥ 0.4" 완화 기준의 유지율. 0.5 경계 근처 규칙은 평균 회귀로 떨어질 수 있어서 같이 본다.

## 3. 방법과 정당화 (루브릭 25점)

### 3.1 빈발 항목집합 (MMDS 6장)

- **A-Priori (§6.2):** 1차 패스에서 상품 빈도를 센다. 2차 패스에서 빈발 상품끼리의 쌍을 삼각 배열로 센다.
- **PCY (§6.3.1):** 1차 패스에서 모든 쌍을 해시 버킷에 센다. 2차 패스에서는 두 상품이 모두 빈발하고 빈발 버킷에 속한 쌍만 센다. 버킷 수는 2^20개, 해시 시드는 0으로 고정한다.
- **교재의 단서:** PCY는 후보가 불규칙해 삼각 배열을 못 쓰고, 쌍마다 12바이트(삼중 표현)가 든다. 그래서 후보를 2/3 이상 줄여야 A-Priori(쌍마다 4바이트)보다 메모리가 적다.
- **주 결과 (결정적):**
  - 2차 패스 후보 쌍 수
  - 빈발 버킷 비율
  - 교재식 이론 메모리. A-Priori는 4 × C(빈발 상품 수, 2) 바이트, PCY는 12 × 후보 쌍 수 + 비트맵 바이트
- **보조 결과 (환경 의존):** 실행 시간과 `tracemalloc` 최대 메모리. 5회의 중앙값과 범위를 실행 환경(CPU, Python 버전)과 함께 보고한다. Python 객체 오버헤드가 섞인 값이라 보조로만 쓴다.
- 비교 수준: support 2%, 1%, 0.5%, 0.25%. 네 수준 모두 두 구현의 빈발 쌍이 같아야 한다.

예상: 파일럿에서 support 1%의 2차 패스는 0.6초였다. 이 규모에서는 PCY가 후보를 2/3 이상 줄이지 못하면 이득이 없다. 결과가 그렇게 나오면 그대로 보고하고, "이 데이터 크기에서는 A-Priori로 충분하다"를 방법 선택의 근거로 쓴다.

### 3.2 규칙과 예측

- **규칙:** 빈발 쌍 {A, B}에서 A → B와 B → A를 만든다. 지표는 support, confidence, lift. H2에는 1년 차 규칙 전체를 쓰고, 2년 차 유지 여부로 거르지 않는다.
- **평가 장바구니:** 2년 차에서 상품 2개 이상인 장바구니 17,515개. 장바구니마다 상품 하나를 seed 0으로 무작위로 골라 가린다.
- **규칙 기반 추천:**
  - 후보: 남은 상품 중 하나를 전건으로 갖는 규칙의 후건. 이미 장바구니에 있는 상품은 뺀다
  - 점수: 후보마다 confidence의 최댓값
  - 동점 처리: support가 큰 순, 그다음 상품 코드 순
  - 5개가 안 되면 기준선 B0 순서로 채운다
- **기준선 B0 (인기 상품):** 1년 차에 가장 많은 장바구니에 들어간 상품 중 장바구니에 없는 5개.
- **기준선 B1 (기준 없는 동시 구매):** 1년 차의 모든 쌍 동시 출현 횟수로 P(y | x)를 계산한다. 남은 상품 x에 대한 최댓값 순으로 추천한다. support 기준이 없다. 이것은 장바구니를 사용자로 보는 아이템 기반 협업 필터링(9장)과 같은 방식이다. 판정 대상은 아니고, support 기준을 둔 것이 득인지 실인지 보여 준다.
- **Bootstrap:** 장바구니 단위로 복원 추출한다 (1,000회, seed 0). 같은 장바구니에서 (규칙 적중 − B0 적중)의 차이를 대응시켜 백분위 신뢰구간을 구한다.
- **층별 보고:** 장바구니 크기 사분위별 HitRate.
- **상품 교체 보고:** 가린 상품이 1년 차에 없던 비율. 그런 장바구니를 뺀 HitRate도 함께 보고한다. 판정은 전체 기준이다.

### 3.3 우연한 규칙 통제 (MMDS §1.2 본페로니 원리)

support 1%에서 함께 나타난 쌍 252,748개를 검사한다. 이만큼 검사하면 우연히 기준을 넘는 쌍이 생긴다.

- **셔플 방법:** (장바구니, 상품) 쌍 전체에서 상품 열만 무작위로 섞는다.
  - 장바구니 크기와 상품별 등장 횟수가 유지되고, 상품 사이의 관계만 깨진다
  - 한 장바구니에 같은 상품이 겹치면 겹친 자리만 다시 섞는다
- **H1a:** 1년 차를 100번 셔플하고 (seed 0~99), 고정한 기준으로 규칙 수를 센다. 실제 규칙 수와 비교한다.
- **H1b의 null:** 2년 차를 100번 셔플하고 (seed 100~199), 실제 1년 차 규칙의 유지율을 잰다.
- **용도:** null은 기준을 정하는 데 쓰지 않는다. 기준은 1절에서 이미 동결했다. null은 결과로만 보고한다.
- **비용:** 1년 차 마이닝 1회가 1초 미만이라 200회도 몇 분이면 된다.

### 3.4 Solar 에이전트

- **모델:** Upstage Solar (OpenAI 호환 chat completions, function calling 지원 모델). 11/17까지 접속 테스트를 하고 모델 ID와 실행 날짜를 `results/agent_runs.jsonl`에 기록한다.
- **도구 (규칙 표만 읽는다. 에이전트는 수치를 직접 계산하지 않는다):**
  - `rules_for(product)`: 상품명 또는 코드로 관련 규칙을 조회한다
  - `top_rules(min_support, min_confidence)`: 기준을 넘는 상위 규칙을 낸다
  - `season_filter(period)`: 성수기 규칙. 1년 차 2009-12와 2010-11 장바구니(4,385개)로 따로 마이닝하고, 이 부분에도 null 100회를 돌린다. 일정이 밀리면 이 도구를 가장 먼저 뺀다
- **평가 세트 (H3):** 질문 25개를 에이전트를 돌리기 전에 만든다. 20개는 답이 있는 질문이고, 5개는 함정 질문이다 (없는 상품, 데이터에 없는 기간, 규칙이 없는 조합).
  - 정답지: 호출할 도구, 인용해야 할 수치, 함정이면 "답할 수 없음"
  - 채점자: 두 명이 따로 채점한다. 불일치 건수를 보고하고 합의로 정한다
- **문항 정답 기준:**
  - 정답지의 수치가 모두 ±0.005 안에서 인용되고, 호출한 도구가 맞으면 정답
  - 함정 질문은 답할 수 없다고 말하면 정답
  - 분모는 정답지 수치이므로, 수치를 인용하지 않은 답은 틀린 것이다
- **비교:** 같은 질문을 도구 없는 Solar에 묻는다. 도구 선택 정확도는 따로 보고한다.
- **실행:** temperature 0으로 돌린다. 그래도 결과가 같다는 보장은 없어서 기록을 커밋하고, 보고서 수치는 이 기록에서만 가져온다.
- **에이전트가 없다면:** 사람이 규칙 수백 개를 표에서 직접 걸러야 한다. 에이전트는 질문을 도구 호출로 바꾸고, 근거 수치와 함께 답한다.

### 3.5 고려했지만 버린 대안

| 대안 | 위치 | 버린 이유 |
|---|---|---|
| Multistage, Multihash | §6.3.2, §6.3.3 | PCY를 더 다듬어 후보를 줄이는 방법이다. PCY의 후보 감소가 작으면 이들도 얻을 것이 적고, 패스나 해시 수만 늘어난다. PCY 결과가 2/3 감소에 못 미치면 이유로 보고한다 |
| SON, Toivonen 표본 알고리즘 | §6.4 | 데이터가 메모리에 다 들어가서 나눠 읽거나 표본을 쓸 이유가 없다 |
| 스트림 빈발 항목 | §6.5 | 데이터가 고정된 2년치다 |
| MinHash + LSH 유사 상품 | 3장 | Jaccard는 대칭이라 "A를 사면 B를 산다"는 방향이 없다. 상품 4,877개라 정확히 셀 수 있어 근사가 필요 없다 |
| 아이템 기반 협업 필터링 | 9장 | 버리지 않고 기준선 B1로 쓴다. 다만 주 방법으로는 쓰지 않는다. support 기준이 없어 드문 쌍의 우연한 동시 출현을 거르지 못하고, 본페로니 통제가 어렵다 |
| FP-Growth | 교재 밖 | 결과는 A-Priori와 같고, 과목 개념을 쓰는 조건에 맞지 않는다 |

## 4. 무엇을 버렸는가 (루브릭 25점)

**"결과가 바뀜"의 정의 (모든 민감도 분석 공통):** H1/H2 판정이 뒤집히거나, 유지율이 10%p 이상 변하거나, HitRate 차이가 2%p 이상 변하는 경우다.

| 버린 정보 | 질문과의 관계 | 확인 방법 |
|---|---|---|
| 수량 | 질문은 "함께 사는가"라 수량은 정의상 무관하다. 다만 도매 대량 구매가 같은 무게로 센다 | 장바구니 총수량으로 가중한 support로 상위 20개 규칙을 다시 뽑아 겹치는 개수 보고 |

| 가격 | 질문과 무관하다 | 해당 없음 |
| 고객 정체성 | 질문은 한 장바구니 안의 동시 구매다. 대신 한 도매 고객의 반복 주문이 일반 규칙처럼 보일 수 있다 | 전처리 6단계의 고객 집중도. 상위 5개 고객이 지지의 50% 이상인 규칙 수 보고 |
| 비회원 거래 (행 22.6%) | 고객 집중도 확인에서 빠진다 | 비회원 장바구니를 뺀 규칙 수와 유지율을 보고 |
| 송장 = 장바구니 | 한 고객이 나눠 낸 주문은 다른 장바구니가 되어 동시 구매가 덜 잡힌다 | 고객 ID를 지우므로 확인할 수 없다. 규칙 수가 과소 추정될 수 있다고 적는다 |
| 같은 줄 반복 (송장-상품 반복 10,941건) | 집합으로 보므로 무관하다 | 해당 없음 |
| 장바구니 안의 순서 | 송장은 한 번에 결제되므로 순서 정보가 원래 없다 | 해당 없음 |
| 상품 교체 | 2년 차 새 상품 651개는 예측할 수 없고, 사라진 상품 917개의 규칙은 자동으로 실패한다 | 3.2절 상품 교체 보고. 사라진 상품이 포함된 규칙 수를 H1b와 함께 보고 |
| support 1% 미만 상품 (롱테일) | 1년 차 상품 4,055개 중 713개만 남는다. 드문 상품에는 규칙이 없다 | 커버리지(추천에 한 번이라도 나온 상품 수)를 B0, B1과 비교 |
| confidence < 0.5 또는 lift ≤ 1 규칙 | 약하거나 음의 관계는 버린다 | 보조로 confidence 0.3 기준 규칙 수와 유지율 보고 |
| 상품 1개 장바구니 (1년 차 1,708개) | 규칙을 만들지 않지만 support 분모에는 들어간다 | 분모에서 뺐을 때 규칙 수 변화 보고 |

## 5. 재현 가능성 (루브릭 15점)

```text
.python-version            3.14 (팀원 전원 같은 버전)
requirements.txt           버전 고정 (pandas, openpyxl, pyarrow, openai)
scripts/download_data.py   다운로드와 SHA 확인 (완료)
src/clean.py               전처리, 단계별 행 수를 results/cleaning_log.csv에 기록
src/apriori.py, src/pcy.py
src/null_model.py          셔플 null
src/evaluate.py            H1, H2 판정, bootstrap, 민감도 분석
src/agent.py               Solar 에이전트. --eval 로 H3 평가 실행 (API 키 필요)
src/run_all.py             키 없이 도는 전체 실행. H3 표는 저장된 기록에서 만든다
tests/test_textbook.py     교재 예제로 A-Priori와 PCY 결과 확인
tests/test_slide_numbers.py  장표 수치가 results/ 파일에 있는지 확인
results/agent_runs.jsonl   에이전트 실행 기록 (커밋)
results/slide_numbers.csv  장표 수치와 출처 파일, 행 (커밋)
```

- 깨끗한 체크아웃에서는 `python scripts/download_data.py && python -m src.run_all`로 H1, H2, 성능 비교, 민감도의 모든 표와 그림을 다시 만든다. API 키가 필요 없다.
- H3를 새로 돌리려면 `.env`에 키를 넣고 `python -m src.agent --eval`을 실행한다. 결과는 달라질 수 있다고 보고서에 적는다.
- 시드: 상품 가리기 0, bootstrap 0, null 0~199, PCY 해시 0.
- 보고서의 그림과 표마다 만든 명령을 바로 아래에 적는다.
- 실행 시간과 메모리는 환경에 따라 달라지므로 보조 결과로만 쓴다. 결정적인 결과(후보 쌍 수, 규칙 수, HitRate)가 주 결과다.
- `.env`와 원본 데이터는 `.gitignore`로 막는다 (`data/` 확인 완료).

## 변경 기록

v0.1 → v0.2 (리뷰 1회차 평균 76.7점 반영)

- support, confidence 기준을 지금 동결했다. null은 기준을 정하는 데 쓰지 않고 결과로만 쓴다. v0.1에서는 H1의 10배 조건이 기준 선택 때문에 항상 참이었다
- null 유지율 정의, 100 seed, 유지율 최소 기준(50%, null + 20%p)을 추가했다. 파일럿 사전 노출도 고지했다
- H2: 규칙 전체 사용, 장바구니 내 상품 제외, 동점 처리, 대응 bootstrap, 최소 효과 +2%p, 기준선 B1, 층별·상품 교체 보고를 추가했다
- H3: 함정 질문 5개, 도구 없는 Solar 비교, 정답지 기준 분모, 채점자 2명을 추가했다
- PCY: 교재의 메모리 단서와 이론 메모리를 주 결과로 했다. Multistage, Multihash를 대안에 넣고, 장 번호(§6.5)와 협업 필터링 설명을 바로잡았다
- 버린 정보 9줄 추가: 큰 장바구니, 비회원, 송장 단위, 같은 줄 반복, 상품 교체, 약한 규칙, 1개 장바구니, 취소 확인, 국가 확인. 민감도의 "결과 바뀜"을 정의했다
- 재현: `run_all`은 키 없이 돈다. 에이전트는 별도 명령이고 기록을 커밋한다. Python 버전 고정, parquet 캐시, 장표 수치 테스트를 추가했다
- 일정: 11/10 부담을 줄이고, 재현 리허설(11/24)과 수치 동결(12/3), 빼는 순서를 추가했다
- 후보 쌍 수의 정의를 바로잡았다 (이론 253,828 vs 실제 252,748). 중복 행의 출처를 나눠 적었다
