# H4 진행 기록

H4는 Solar가 1차 통계와 메모리 예산을 보고 집계 설정(Apriori, PCY 버킷 65,521개, PCY 버킷 1,048,573개)을 고르는 확장이다. 출처는 `Basket Insight Agent 프로젝트 수정안.docx`(레포 밖)이고, 11/20 검토는 [`change_requests.md`](change_requests.md)에 있다. 동결된 `plan_v0.6`의 H1~H3 판정과 분리한다.

이 파일은 H4 작업이 진행될 때마다 맨 아래 "기록"에 날짜와 함께 한 줄씩 더한다.

## 첫 목표

Solar가 설정을 골라 작업 한 건을 끝까지 완료한다 (화면에서 제출 → 설정 선택 → 전체 집계 → 결과 조회).

## 진행 계획 (11/24 결정: H4를 시연까지 진행한다)

2. 세 선택 방식(규칙 기반, Solar 1회, Solar + 시험 집계)을 같은 조건에서 반복 측정해 비교표를 채운다.

4. 보고서 부록과 장표에 H4 결과를 싣는다.

### 판정 기준 (실험 전에 확정한다)

수정안의 질문은 "Solar가 필요한 경우에만 추가 측정을 요청하면, API 호출 시간까지 포함해 규칙 기반 선택보다 더 나은 실행 결정을 내릴 수 있는가"다. 제안하는 "예" 조건은 둘 다 충족이다.

1. 모든 조건에서 Solar 방식의 빈발 쌍과 건수가 고정 방식과 같다.
2. 조건 중 하나 이상에서 Solar 방식의 전체 시간 중앙값(선택 시간 포함)이 규칙 기반보다 짧다.

사전 노출: 11/24에 각 1회씩 6건을 돌려 결과를 봤다. 지지도 1%, 예산 64 MiB에서 Solar는 규칙 기반보다 나쁜 설정을 골랐고 선택에 약 5초가 걸렸다. 보고서에 이 사실을 적는다. 결과가 "아니오"여도 그대로 보고한다.

### 실험 조건 (제안)

| 조건 | 입력 | 지지도 | 예산 | 예산을 통과하는 설정 |
|---|---|---|---|---|
| B0 | `y1` | 1% | 64 MiB | 셋 |
| B1 | `y1` | 1% | 3.5 MiB | `apriori`, `pcy_small` |
| B0.25 | `y1` | 0.25% | 6 MiB | `pcy_large` |
| B0.25-all | `all` | 0.25% | 6 MiB | `pcy_large` |

조건 4개 × 방식 3개 × 반복 5회 = 작업 60건이다. Solar 호출은 약 40~80회, 전체 실행은 10분 안쪽이다. 반복 횟수는 유찬이 확정한다.

### 시연 (발표 12분 중 약 2분)

수정안대로 미리 실행해 검증한 사례만 쓴다.

| 순서 | 사례 | 보여 줄 것 |
|---|---|---|
| 1 | `y1`, 1%, 64 MiB, 규칙 기반 | 기준선. 세 설정이 모두 예산에 들고 `apriori`를 고른다 |
| 2 | `y1`, 0.25%, 6 MiB, Solar + 시험 집계 | 예산이 설정을 가려낸다. Solar가 표본 집계를 요청하고 `pcy_large`를 고른다 |
| 3 | `y1`, 1%, 64 MiB, Solar 1회 | Solar가 `pcy_small`을 고른 사례. 규칙 기반보다 느리다는 점을 그대로 보여 준다 |

- 사례 2만 발표 중에 새로 제출한다 (약 9초). 사례 1과 3은 저장된 작업을 주소로 연다 (`#jobs/번호`).
- 대체 수단: Solar가 응답하지 않으면 서버가 규칙 기반으로 넘어간다. 네트워크가 없으면 저장된 작업 세 건을 주소로 열어 보여 준다. 화면 캡처도 장표에 넣어 둔다.

### 하지 않는 것

접수 순서 대 마감 우선 실행 비교, 장바구니 수·상품 종류 수를 바꾼 반복 측정, 운영체제 강제 메모리 한도, 외부 배포. 수정안도 이들을 확장 범위로 두었다.

## 알려진 사실

- 기준 PC에서 `profile()`은 0.39초다. 1년 차 전체 집계(지지도 1%에서 A-Priori 0.13초, PCY 0.40초)보다 길거나 같다. 지금 데이터 크기에서는 선택 비용이 집계 절감보다 크다.
- 지지도 1%에서는 어떤 예산에서도 모델 메모리가 Apriori가 가장 작다(1,015,312 B). 선택이 갈리는 조건은 지지도 0.25%, 예산 6 MiB다.
- `pilot()` 기본값(장바구니 1,000개)의 빈발 쌍 수는 전체 결과와 크게 다르다. 시간 추정용으로만 쓴다.
- H3 채점은 `agent-v1`(29e3d29)로 고정돼 있다. H4 변경은 H3 점수에 영향이 없다.

## 기록

### 2026-11-25: 정고은 시연 확인 (Windows)

- 크롬 화면에서 세 시연 조건을 제출하고 자동 갱신, 선택 이력, 결과 표와 CSV 링크를 확인했다. 실제 Solar 도구 호출의 응답이 `MiningSelector`의 `pilot`과 `choose` 처리 및 화면 이력과 맞았다.
- 발표 순서: ① 작업 1, `y1` 1%, 64 MiB, `rules` → `apriori`, 빈발 쌍 585개. ② 작업 2, `y1` 0.25%, 6 MiB, `solar_pilot` → 표본 시험 1회 후 `pcy_large`, 빈발 쌍 26,111개. ③ 작업 4, `y1` 1%, 64 MiB, `solar_once` → `pcy_small`, 빈발 쌍 585개. 작업 3은 입력 실수로 별도 제출된 추가 시험이며 시연 순서에서 제외한다.
- 1%의 작업 1과 4는 모든 쌍과 건수가 같았고, 0.25% 작업 2는 고정 Apriori의 모든 쌍과 건수와 같았다. Windows에서는 `resource` 측정을 지원하지 않아 프로세스 메모리가 표시되지 않는다. 이 값은 1회 시연 결과이며 반복 실험의 비교표에 쓰지 않는다.
- 작업 2의 Solar 설명은 6 MiB 예산을 약 62.9 MB로 잘못 언급했다. 실제 선택의 예산 검사는 별도로 통과했으나 생성 설명의 수치는 검증하지 않으므로 화면에 이를 표시했다. 발표에서 수치는 시스템의 입력 통계·예산을 기준으로 확인한다.
- 위 작업 번호와 SQLite/CSV는 **정고은 Windows PC의 로컬 `data/jobs/`에만 있다**. 다른 PC에서는 같은 주소와 번호가 자동으로 생성되지 않는다. 발표 PC에서 동일 조건을 사전 실행하고 저장된 작업 주소와 화면 캡처를 다시 확보한다. 규칙 기반 및 Solar 1회 선택은 저장된 작업을 열고, 표본 시험 사례는 발표 중 새로 제출하는 순서를 따른다. Solar 실패 시 규칙 기반 전환을 보여 주고, 네트워크 장애에는 사전 화면 캡처를 대체 수단으로 쓴다.
- Windows에서 SQLite 연결이 닫히지 않아 임시 테스트 DB 정리가 실패하던 문제를 수정했다. `tests.test_jobs`와 선택기 테스트가 통과한다. `goeun-solar-selection`에 푸시하지 않은 로컬 커밋이나 변경은 없었다.
